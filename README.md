# مين طالب شو؟ — React Student Starter

إعداد: Yanal Abuhadhoud · Version 1.1

مشروع تدريبي فردي لطلب طعام جماعي للمكتب. الواجهة فارغة عمدًا؛ تبنيها بنفسك.
البنية الجاهزة توفّر 29 API محاكاة باستخدام MSW داخل المتصفح، دون Backend حقيقي.

## التشغيل

يلزم Node.js بإصدار 22.12 أو أحدث. افتح الطرفية داخل هذا المجلد:

```bash
npm install
npm run dev
```

افتح عنوان Local (localhost) الذي يطبعه Vite، وليس عنوان Network؛ المحاكاة تحتاج localhost أو HTTPS لتشغيل Service Worker. الصفحة الرئيسية فارغة لأن App.jsx يرجع null.
ابدأ كتابة تطبيقك في src/App.jsx. React Router وRedux Toolkit وReact Redux وAxios مثبتة،
لكن لم يتم إعداد صفحات أو Store أو Context أو حلول مهام للطالب.

افتح من نفس عنوان التشغيل:

- `/Requirements.html`: جميع المتطلبات، 33 تاسك، قواعد العمل وشروط القبول.
- `/API_Guide.html`: توثيق العمليات الـ29، أمثلة Request/Response وأخطاء وصلاحيات.
- `/mock-tools.html`: فحص APIs وتصدير/استيراد البيانات والتأخير والأخطاء التجريبية.

## البداية المقترحة

1. اقرأ المتطلبات وافتح أدوات المحاكاة.
2. جرّب Login في أدوات المحاكاة؛ يتم ملء Token تلقائيًا عند نجاحه.
3. جرّب Me ثم GET /api/restaurants.
4. ابدأ تنفيذ الصفحات والمسارات، ثم AuthContext وuseAuth وحماية الصفحات.
5. نفّذ التاسكات بالترتيب. لا تغيّر قواعد المحاكاة لتجاوز خطأ أو صلاحية.

## استدعاء APIs

- جميع المسارات تبدأ بـ `/api`.
- كل العمليات تحتاج `Authorization: Bearer YOUR_TOKEN` ما عدا Register وLogin.
- أرسل JSON مع `Content-Type: application/json`.
- النجاح: `{ "data": ... }`، والخطأ: `{ "error": { "code": "...", "message": "..." } }`.
- الجلسة التجريبية مدتها 8 ساعات، والـ token ليس JWT.
- استخدم `fetch` أو `Axios` داخل التطبيق. MSW يعمل في المتصفح؛ Postman وcurl لا يشغّلان هذه APIs.
- استخدم `sessionStorage` لحفظ token التجريبي في واجهتك، ولا تحفظ كلمة المرور.
- جميع المبالغ عدد صحيح بالفلس: 4500 يعني 4.500 JOD.
- جميع التواريخ ISO مع المنطقة الزمنية، وحالات الطلب حساسة للأحرف.
- startup في src/main.jsx يجهّز المحاكاة قبل Render. احتفظ بهذا الترتيب.

## أين توجد البيانات؟

`public/data/db.json` هو ملف بيانات البداية.
عند أول تشغيل تنسخ المحاكاة محتواه إلى localStorage تحت المفتاح `meen-talab-sho.db.v1`.
كل العمليات التالية تحفظ البيانات تلقائيًا في هذا المفتاح وتبقى بعد Refresh.

**التغييرات لا تكتب تلقائيًا فوق ملف db.json على القرص.**
من `/mock-tools.html` اضغط «تصدير JSON محدث» لتحصل على `db-export.json`.
يمكنك استيراده من نفس الصفحة. التصدير يستبعد sessions، والاستيراد ينهي كل الجلسات.
يمكن وضع النسخة المصدّرة بدل public/data/db.json ثم استخدام «إعادة بيانات البداية».
تعديل الملف وحده لا يستبدل بيانات متصفح سبق تهيئتها. صدّر نسخة قبل الاستبدال أو إعادة الضبط.

محتوى JSON:

- users: حسابات وهمية وكلمات مرور تدريبية ظاهرة.
- sessions: جلسات المحاكاة الحالية محليًا؛ لا تُضمّن في التصدير.
- restaurants: المطاعم وحالة الفتح.
- menuItems: المنتجات والتصنيفات والأسعار بالفلس وحالة التوفر.
- orders: الطلبات وأعضاؤها وسلالهم وحالات الدفع ونسخة الفاتورة المثبتة.

القيم مثل `$NOW+3600000` تُحوّل إلى وقت بعد ساعة عند التهيئة أو إعادة الضبط.
الأوقات الفعلية في JSON المصدّر لا تتحرك تلقائيًا عند الاستيراد؛ قد يكون الطلب مغلقًا إن مرّ موعده.

## تجربة أكثر من مستخدم

افتح تبويبين من نفس المتصفح ونفس عنوان localhost. البيانات مشتركة محليًا،
أما sessionStorage فمستقل لكل تبويب. سجّل الدخول بالحساب المقصود في كل تبويب؛
قد ينسخ المتصفح token مبدئيًا عند فتح تبويب من آخر.

لا يوجد Real-time: أعد جلب البيانات عند التحديث. المتصفحات والأجهزة المختلفة
لا تتشارك البيانات. تغيير منفذ التشغيل أو اسم الموقع يعطي مساحة تخزين مختلفة.
المحاكاة تستخدم Web Locks عند توفرها لتسلسل التعديلات بين التبويبات؛ في متصفح لا
يدعمها، استخدم تبويبًا واحدًا مع تبديل الحسابات لتجنب تعارض الكتابة.

## الأخطاء التجريبية

من أدوات المحاكاة يمكنك ضبط تأخير 0–10000 ms، وإفشال طلب API قادم مرة واحدة برمز 503.
هذه الإعدادات تخص التبويب نفسه: اضبطها ثم ارجع إلى التطبيق في التبويب ذاته.
الفشل يصيب أول طلب API بعدها. عند الرجوع يُعاد تحميل التطبيق، فإذا كنت مسجّلًا يكون أول طلب غالبًا /api/auth/me.
الفشل يحدث قبل تغيير البيانات. زر «إنهاء جميع الجلسات» يجعل الطلبات المحمية التالية ترجع 401.
الـ token في أدوات المحاكاة مستقل عن token واجهتك، ولا يتم تسجيل دخوله فيها تلقائيًا.

## ما الذي أعدّله؟

اكتب الواجهة في App.jsx ومجلدات components/pages/hooks/context/store/services.
مجلد src/mocks والـ Service Worker وتجهيز main.jsx أجزاء جاهزة.

الحساب المالي تعيده المحاكاة؛ عليك عرضه وفهمه، وليس إنشاء Backend آخر.

المشروع للتعليم فقط: كلمات المرور والبيانات قابلة للعرض محليًا، وtoken تجريبي.

## إدارة المطاعم والجروبات

المطعم سجل بيانات فقط، ولا يمتلك حسابًا أو تسجيل دخول.
الأدمن (admin@example.test / Demo123!) يضيف المطاعم ويعدّلها ويضيف منتجاتها.
user.role يرجع admin أو member من Login وMe. التسجيل العام ينشئ member فقط ويرفض إرسال role.
إدارة الكتالوج لا تمنح الأدمن صلاحيات على طلبات غيره؛ صلاحية المنظّم مرتبطة بكل orderId.
يستطيع الأدمن إنشاء طلب أو الانضمام برمز كأي عضو، ويكون منظّمًا في طلبه فقط.

مسارات الأدمن، وكلها تحتاج حساب admin:

- POST /api/admin/restaurants: إضافة مطعم مغلق.
- PATCH /api/admin/restaurants/:restaurantId: تعديل المعلومات وisOpen؛ التفعيل يحتاج منتجًا متاحًا.
- POST /api/admin/restaurants/:restaurantId/menu: إضافة منتج.
- PATCH /api/admin/restaurants/:restaurantId/menu/:productId: تعديل السعر أو التوفر أو الاسم أو التصنيف.

لا توجد عمليات حذف للمطاعم أو المنتجات؛ استخدم حالات الإتاحة للحفاظ على السجلات.
تغيير سعر المنتج يؤثر على التقديرات قبل Confirmed، أما الفواتير المثبتة فلا تتغير.
إغلاق المطعم يمنع إنشاء طلبات جديدة، وإضافة عناصر السلال وتعديلها، والتأكيد للطلبات غير المؤكدة،
دون إلغاء الطلبات تلقائيًا. حذف عناصر السلة يبقى متاحًا. تعطيل آخر منتج متاح لا يغلق المطعم تلقائيًا،
لكن إنشاء الطلبات منه وتعديل المطعم وهو مفتوح يُرفضان بـ MENU_EMPTY.

كل جروب هو طلب وجبة مستقل، وليس مجموعة دائمة. يمكن تشغيل عدة جروبات من مطاعم مختلفة
أو من نفس المطعم؛ لا تندمج تلقائيًا. العضو يمكنه الانضمام لأكثر من جروب، ولكل orderId سلته وحسابه.
